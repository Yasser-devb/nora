# Nora Reactive UI Engine

**Status:** Experimental vertical slice implemented and locally verified.
This is not a stable public API or production-readiness claim. Only behavior
listed under "Implemented and verified slice" is current; the rest is proposed
and must not be presented as a current feature.

## Product goal

Nora intends to make server-rendered, PHP-authored interfaces reactive through
a framework-owned browser runtime. Developers should compose a page and
components in PHP and Nora templates without creating JavaScript, mounting
islands, or manually synchronizing component boundaries for ordinary
interactions. This is a target, not a claim that Nora already supports a
React-equivalent UI framework.

## Implemented and verified slice

Existing code provides `Application`, registration-order routing and
middleware, session storage, CSRF token management, authorization primitives,
validation, and HTML-escaped `.nora` templates. The reactive slice is an
opt-in, single-page component API with a session-owned page state and a
first-party delegated browser runtime.

The generated-app Playwright test verifies the following complete flow:

1. A route creates a server-rendered document and mounts one page component.
2. The browser automatically loads Nora's runtime asset with HTTP 200.
3. Delegated DOM events call an explicitly allowlisted page action over a
   same-origin JSON `fetch`.
4. The PHP server validates the action name and argument schema and applies
   the configured authorization callback. The companion PHP integration
   suite separately verifies CSRF/origin checks, page ownership, and stale
   revision/replay rejection.
5. PHP applies the action to the session-owned state, increments its
   revision, and renders the page again.
6. The browser reconciles the returned HTML within the single document root;
   the verified interaction updates outputs without reloading the document.
7. The test verifies a changed output in both adjacent keyed template
   sections, preserves an input's typed value, and verifies focused control
   and text selection preservation across compatible updates.
8. It tampers with browser action markup and arguments, verifies unknown
   actions receive 404, invalid arguments receive 422, and a denied
   authorization callback receives 403 without changing rendered state.
9. Browser-visible error text is checked for generic safe messages and absence
   of stack traces/internal paths.

The test is one local Chromium scenario against a clean app generated by the
Nora CLI and served by PHP's development server. It does not establish a
cross-browser support matrix, hosted CI success, or production fitness.

The runtime treats page state and the page revision as server-authoritative.
The browser sends only an opaque page handle, expected revision, explicit
action name, and action arguments. It never submits authoritative state or
arbitrary PHP method names. A page handle is random and its record is scoped
to the current PHP session. PHP's session lock serializes requests for the
same session; a stale revision is rejected and reconciled with current HTML
instead of replaying the action.

## Component and action contract

The prototype has a registered `ReactiveComponent` per page type. A component
provides initial state, rendering, and an explicit map of action names to
`ReactiveAction` definitions. An action definition declares its argument
validation rules, state transition, and optional authorization callback.
Callbacks are registered in trusted PHP; a request cannot select a PHP method
or component class. Authorization is checked on every server action. Missing
authorization callbacks deny by default. Intentionally public actions must
use `ReactiveAction::publicAction(...)`; protected actions must provide an
explicit callback that returns `true` only when authorized. Authorization
callbacks should be side-effect free; transitions run only after successful
authorization.

The experimental prototype currently represents page state as bounded
JSON-safe associative arrays. One registered page component renders a
document; the generated sections are template partials sharing that page's
state, not independent reactive components. It does not yet expose typed
state/props value objects, computed values, lifecycle hooks, or an independent
nested-component composition API. These require design and compatibility
review before the API is stabilized.

One page is the consistency boundary for the initial slice. All visible
components/partials on that page are rendered from the same authoritative
page state and use one event-delegation root. Adjacent counter displays are
the first shared-state example. Independent child state, component ownership
maps, child lifecycle hooks, cross-page state, and fine-grained component
subscriptions are not implemented.

## Rendering and browser update model

- Initial requests render complete HTML on the server for discoverability,
  first paint, and operation without JavaScript.
- The runtime script is served from a fixed framework endpoint and loaded by
  the framework-generated document shell.
- Events marked with a server-rendered `data-nora-action` attribute are
  delegated at the document root. No per-component hydration or JS
  registration is required.
- Server responses carry rendered page-root content and the new revision.
  The runtime parses that same-origin response and reconciles keyed nodes
  (`data-nora-key`) while reusing compatible existing nodes.
- The generated browser scenario verifies node identity, input value, focus,
  and selection preservation in its compatible keyed-node cases. This is not
  a general guarantee for every control type or arbitrary tree update.
  Stable keys are required for reorderable lists; the current prototype's
  reconciler is not a general virtual DOM and has no list diff guarantee.
- Server rendering after each server action is acceptable for the first
  slice, but the browser must not perform a full-page navigation. Response
  size and render cost must be measured before broader claims are made.

Simple local interactions (for example, opening a disclosure) may later run
in the runtime without a request when no server-authoritative decision is
needed. Persistence, permissions, and authoritative validation remain
server-controlled. No persistent socket is proposed for the initial model;
HTTP fetch is simpler to deploy and test. A persistent transport should be
considered only for a measured real-time use case.

## State, validation, and security boundaries

- Page state is stored in the PHP session, not serialized to the browser.
- Page handles use cryptographically secure randomness and must resolve
  within the current session.
- At most 32 reactive page records are retained per session; inactive records
  expire after 30 minutes and are pruned on the next reactive page/action
  request.
- `ReactiveEngine` prepends its session middleware so session-dependent
  middleware already registered on the application runs only after the
  session has started.
- Requests are size-bounded, JSON-only, and have a strict top-level schema.
  Content-Type must be `application/json` (optionally with parameters);
  JSONP and other media types are rejected.
- Action names and argument fields are allowlisted; unknown argument fields
  are rejected, and declared values use the existing `Validator`.
- Component state must be bounded JSON-safe scalars/arrays; objects, resources,
  and arbitrary PHP serialization are prohibited.
- The expected revision prevents stale or replayed state transitions from
  being applied twice. The server session lock serializes updates within the
  same session. The browser does not automatically retry a mutation.
- Unsafe requests require the existing session CSRF token in a request header.
  SameSite cookie behavior is defense in depth, not a replacement for token
  checking. Deployments must use HTTPS and secure cookies in production.
- Actions with no policy are denied. Protected actions re-evaluate
  authorization on each request. `ReactiveAction::publicAction(...)` is the
  explicit opt-in for public-to-page-holder actions. Hiding a control in HTML
  is not authorization.
- Dynamic template values must use `TemplateRenderer` or equivalent
  context-correct escaping. HTML-text escaping is not safe for JavaScript,
  CSS, or URL contexts. Never render untrusted values as markup.
- The protocol must not expose component objects, services, session contents,
  credentials, or internal exception details.
- Validation, stale revision, missing page, CSRF, and authorization failures
  return explicit statuses and do not mutate server state.
- Mutating actions with external side effects may need a durable idempotency
  key or application-level transaction; a session revision alone is not a
  distributed exactly-once guarantee.

## Nested components and shared state

The target model is one document-level runtime and a server-rendered component
tree. Component keys identify stable rendered nodes; they are not bearer
credentials. An action is dispatched through the registered page/component
definition, and state ownership is explicit. Parent/child communication
should flow through declared props/events or shared page state rather than
implicit global mutation. Every child action must resolve through the same
page/session authorization boundary.

The first slice deliberately coordinates adjacent markup through a single
page state rather than introducing an incomplete child-state protocol.
Child-local state, ownership enforcement between independent components,
component lifecycle restoration, and reusable nested class composition are
future work.

## Errors and connection recovery

- Invalid JSON/schema: `400`; oversized request: `413`; unsupported media:
  `415`; missing/foreign page: `404`; invalid CSRF or denied action: `403`;
  stale revision: `409`; invalid action arguments: `422`.
- On success, the runtime applies the server's rendered update and revision.
- On a stale response, the server returns current rendered HTML and revision;
  the runtime reconciles them and reports the conflict without replaying the
  mutation.
- On network failure, the runtime leaves the last confirmed UI intact,
  announces the error with a text-only live status region, and does not
  automatically resubmit.
- Server exceptions use Nora's centralized exception handling and do not
  return stack traces in production.

Retry affordances, queued actions, offline behavior, and reconnect semantics
are not implemented in the prototype and must be designed around idempotency.

## Progressive enhancement and accessibility

Server-rendered content is visible without JavaScript. An action control
should remain a real semantic HTML control; without the runtime, action
controls must not falsely claim successful state changes. Future form and
navigation APIs must preserve native semantics and meaningful error behavior.
Runtime status and errors use text-only `aria-live` announcements, actions
must be keyboard operable, and focus should remain stable after updates.
Automated accessibility review and production navigation behavior are future
work.

## Performance and compatibility

The prototype uses fetch and DOMParser, supported by current evergreen
browsers. Nora has not published a formal browser support matrix. Do not claim
speed superiority over React, Livewire, or other tools without repeatable
benchmarks. Measure runtime download/compressed size, request payload/response
size, render/action latency, reconciliation work, and page/component counts.
Persistent connections, partial server rendering, caches, and speculative
optimistic updates require evidence before adoption.

## Test and debug requirements

Tests must cover server rendering, CSRF, session/page isolation, unknown
actions and fields, invalid arguments/state, authorization denial, stale
revisions, XSS escaping, bounded payloads, and action non-mutation on failure.
Browser tests must exercise the official script, click-to-PHP round-trip,
no-navigation behavior, shared adjacent output, focus/input preservation,
keyed identity, errors, and a clean generated app. Debugging must not expose
session state or secrets; optional development diagnostics should be
redacted and disabled in production.

## Architecture diagram: initial HTTP action

```mermaid
sequenceDiagram
    participant Browser
    participant Runtime as Nora browser runtime
    participant App as Nora Application
    participant Session as PHP session
    participant Component as Registered PHP page component
    participant Validator
    participant Auth as Action authorization

    Browser->>App: GET mounted page
    App->>Session: start and load session
    App->>Component: initialState and render
    Component-->>App: escaped server HTML
    App-->>Browser: HTML + CSRF token + page handle + runtime script
    Browser->>Runtime: delegated action event
    Runtime->>App: POST page/action/args/revision + CSRF
    App->>Session: start; resolve page only in this session
    App->>Validator: validate exact action arguments
    App->>Auth: re-check this action
    App->>Component: apply allowlisted transition
    Component-->>App: new state and rendered root
    App->>Session: persist state and increment revision
    App-->>Runtime: JSON containing HTML and revision
    Runtime->>Browser: keyed in-place DOM reconciliation
```

## Further target design areas

Reactive forms and field binding, nested component ownership, local UI
behaviors, computed values, lifecycle hooks, navigation/history, validation
presentation, uploads/progress, optimistic UI, more robust connection
recovery, formal browser support, benchmarks, and complete API ergonomics are
not part of the initial vertical slice.
